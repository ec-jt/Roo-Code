# Roo Code 4.2.103 - Cordis preview 99

Extension version: **4.2.103**. Git tag: **v4.2.103-cordis-preview.99**. This is an experimental GitHub prerelease. It is not a stable release or a marketplace release.

This release makes **modes** the default task profile again (ADR-2026-11-23-modes-default-profile). It also fixes the 7 defects found in the long-horizon evaluation L1 (evaluation-2026-11-22-long-horizon, section 7).

## Changed: modes is the default task profile

A new top-level task now resolves its profile in this order:

1. the stored task profile (Settings > Experimental > Task profile) when it is set;
2. otherwise `cordis`, only when `experiments.cordisRuntimePreview: true` is stored;
3. otherwise `modes`. An absent value now means modes, not cordis.

- The `cordisRuntimePreview` experiment default is now off. Stored values are not rewritten (C-5).
- Settings > Experimental shows `modes` when nothing is stored.
- Existing tasks keep their stored profile. Child tasks inherit their parent's profile, as before.
- The `/plan` handler, the preview runtime and the kill switch follow the new default. With nothing stored, `/plan` with no open task shows the "Cordis and hybrid tasks only" notice and creates no task.

**To opt in:** open Settings > Experimental, set Task profile to Cordis or Hybrid, and press Save.

Users who had `cordisRuntimePreview: true` stored stay on cordis. This includes users whose older version saved every default. Without a migration, the stored value cannot be told apart from an explicit choice, and no migration is done.

## Fixed: `task_state` calls were never auto-approved (L1 defect 1)

Model `task_state` calls use the ordinary chat approval. Now, when auto-approval is on:

- a `read` is auto-approved when the read-only category is on;
- a `patch` is auto-approved when the write category is on.

Each action asks when its category is off. "All actions" alone does not approve it. A task-local mandatory approval still asks. Panel actions keep their native review.

## Fixed: Cordis `/plan` created no architecture records (L1 defect 2)

- With architecture context on, a workspace with no `docs/architecture/`, and bootstrap on, a task with the plan overlay now gets the bootstrap block in any mode, not only in Architect mode. The block also tells the model to record the key constraints and decisions of the plan as records before it calls `exit_plan`, and to cite their IDs in the plan.
- The plan overlay prompt states the same rule.
- The cordis and hybrid drift rules now also cover requirements stated earlier in the task and the approved plan, even when no record exists. A later message that conflicts with them is reported through an `exit_plan` amendment and is not implemented silently.

## Fixed: Save from a settings view that was open a while overwrote newer settings (L1 defect 3)

- Save now sends only the fields changed in the view. Experiments are sent one by one, and the extension merges them into the stored object.
- A view with no unsaved changes takes newer extension state when it arrives.

## Fixed: turning task state on could leave no ledger and no error (L1 defect 4)

- "Enable task state" now checks that the ledger was written.
- A failed enable also shows a native error message. Before, the panel could drop the error when an Orchestrator child had become the current task. A cancelled review shows no error.
- The Task state panel shows the task it applies to (task ID and title).
- For a subtask, the panel says that task state applies only to the subtask, not to its parent. It also says how to enable task state for the parent.

## Fixed: `dispatch-failed` after a `browser_action` launch needed a manual Continue (L1 defect 5)

When the pinned task-state recall becomes stale because of the task itself, the request is prepared again once, with no prompt. This covers the task's own history change, or a model or runtime revision with recall still on. A user change to task state, a second stop in a row, or recall being turned off still stops and asks.

## Fixed: a queued chat message answered an open tool approval (L1 defect 6)

A message typed while a `tool`, `command`, `use_mcp_server`, `browser_action_launch` or `computer_action` approval is open is no longer used as the answer. It stays in the queue until the user approves or rejects. It is then delivered with that decision, as feedback. Follow-up questions and completion feedback still take a queued message as before.

## Fixed: the parent did not see user messages sent to a child (L1 defect 7)

When a subtask returns, its result now ends with "User messages received by the subtask:", followed by each user message the child received. At most the last 20 messages are listed, each up to 4,000 characters. Messages are not rerouted: the user still talks to the visible child.
