# Roo Code 4.2.86 - Cordis preview 82

Extension version: **4.2.86**. Git tag: **v4.2.86-cordis-preview.82**. This is an experimental GitHub prerelease. It is not a stable release or a marketplace release.

This release fixes three defects found in the 4.2.85 live checks: `task_state` and `memory` now accept the string `"null"`, you can enable task state before the first model turn or while a question is pending, and the offload count is reported when a summary follows.

## 1. `task_state` and `memory` accept the string `"null"`

In 4.2.85, DeepSeek (`deepseek-flash`) sent `{"action":"read","operations":"null"}`. Schema validation rejected the call, because only a missing value or an empty string counted as `null`.

Now:

- `task_state`: `expected_revision` and `operations` treat the string `"null"` as `null`. The match trims whitespace and ignores case, so `"NULL "` also counts.
- `memory`: `expected_revision` gets the same treatment. `id` and `type` do too, when they are present, because `"null"` can never be a valid UUID or topic type. Free-text fields (`name`, `description`, `body`, `query`) are unchanged, because `"null"` can be real content there.
- **A write is still refused without a revision.** A `task_state` patch with `expected_revision: "null"` returns `REVISION_REQUIRED` and writes nothing. A `memory` update or delete behaves the same way.

## 2. Enable task state at any time

**Cause.** The task-state panel's **Enable task state** button sends a native `initialize` request. The extension checked that request with `Task.assertTaskStateNativeAllowed()`, the same idle-only check used for every native task-state change. That check fails in these cases:

- the task is not yet initialized
- a request is streaming, being prepared or loops
- tool results are pending (`userMessageContent`)
- an admission is pending
- a terminal is running

In practice this blocked enabling during the first turn of a new task and in other busy states. The user saw only `Task-state review requires the current idle task with no pending tool results` in the panel. The extension did not log the error.

**Fix.**

- **New guard for initialize only.** `initialize` now uses a narrower guard, `Task.assertTaskStateEnableAllowed()`. It requires:
    - the current open task, which must not be aborted, abandoned, closed, or closed for persistence
    - no prepared replay
    - no assistant history edit
    - no context recovery
- **Why the narrower guard is safe.** Initialize can only create a ledger where none exists. The store rejects a second initialize with `CONFLICT`. A turn already in progress has no pinned recall, so the new ledger takes effect at the next turn boundary.
- **Checks that still apply to initialize:**
    - native confirmation
    - workspace trust
    - `.rooignore` and write-protection checks
    - the epoch and history-anchor check during authorization
- **Other actions are unchanged.** Correct, configure, disable, fork, start, attest and fresh context still require an idle task.
- **Failures are logged.** The extension now logs every failed task-state request, including malformed ones, to the Roo Code output channel. The panel still shows the error.
- **DISABLED result.** When the model calls `task_state` before you enable it, the result is still `DISABLED`. The result now tells the model to ask the user to enable task state in the task panel and to continue without it until then. This result does not set the failed-turn flag. It never counted toward the mistake limit, and it still does not.
- **Tool description.** The `task_state` tool description now says that only the user can enable task state.
- **Auto-enable.** Task state is still never enabled automatically.

## 3. Offload and prune counts are kept when a summary follows

In 4.2.85, if image offload or tool-result pruning ran but did not free enough context, the summary (or the truncation fallback) ran next. The row for that step did not show the offload or prune counts.

Now:

- `manageContext` returns `prunedCount` and `offloadedCount` on the summary result and on the truncation fallback result.
- The `condense_context` row (`contextCondense`) and the `sliding_window_truncation` row (`contextTruncation`) carry the counts as optional fields.
- The condense, truncation and prune rows show the counts, for example "Saved 3 older images to the task folder and replaced them with references." These rows reuse the existing `chat:contextManagement.prune.*` strings, so this release adds no new UI strings.

## Installed version requires a reload

Installing a VSIX does not activate it. A running editor keeps its current extension version until you reload the window.

## Storage and rollback

This release adds no settings. Stored UI rows can contain two new optional fields, `prunedCount` and `offloadedCount`. Older versions ignore these fields.

If you roll back to 4.2.85:

- The string `"null"` fails validation again.
- Task state can be enabled only while the task is idle.
- Counts that are already stored do not appear on condense and truncation rows.
