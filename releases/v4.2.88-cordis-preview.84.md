# Roo Code 4.2.88 - Cordis preview 84

Extension version: **4.2.88**. Git tag: **v4.2.88-cordis-preview.84**. This is an experimental GitHub prerelease. It is not a stable release or a marketplace release.

This release fixes two defects found in the 4.2.87 live checks. The chat window did not show the prune and offload counts. A DeepSeek `task_state` read still failed with the generic schema error. Schema errors now also name the failing field.

## 1. Context preview rows show tokens, cost and counts

In 4.2.87, a live task condensed twice. One condense row had `prunedCount: 1, offloadedCount: 3`. The chat showed only "Context summary (preview)", the summary text and the buttons. There was no token line, no cost and no count.

**Cause.** The chat window cuts a condense summary to about 2.7 KB and marks the row as a preview. Most real summaries are longer, so the row is almost always a preview. Preview rows render as a plain history row, and that row did not show the context data. The counts were present in the row data but were never displayed.

**Fix.** The plain history row now has a context header for `condense_context`, `sliding_window_truncation` and `context_pruned` rows:

- tokens before and after
- the cost badge (condense rows with a cost)
- the pruned and offloaded counts, with the same `prune.description` and `prune.offloaded` text as the full rows

The preview text, "Open full message" and the recover control are unchanged. Other row types are unchanged. The size limits are unchanged.

## 2. `task_state` read ignores revision and operations

In 4.2.87, DeepSeek (`deepseek-flash`) sent a `task_state` read three times. Each call failed with "Arguments do not match the tool schema" and the task reached the mistake limit. API history stored the call as `{"action":"read","operations":"null"}`, which the parser accepts.

**Cause.** The stored input was not the raw call. For a rejected call, history was rebuilt from the string params. That conversion drops keys that are not general tool parameters, such as `expected_revision`, and turns `null` into the string `"null"`. A raw read with any non-null `expected_revision` (for example a placeholder or an old revision) produces exactly the stored input. The parser rejected such a read with "Read requires null revision and operations".

**Fix.**

- **Read.** A read uses neither `expected_revision` nor `operations`, so the parser now sets both to null for a read. A read is read-only, so this is safe.
- **Patch.** Unchanged. A patch still requires the exact revision from the last read, approval and the authorization checks.
- **History.** A rejected call now keeps the exact JSON object the model sent in API history, so the model and later diagnostics see the real mistake. It is never executed.

## 3. Schema errors name the failing field

The generic parser error now names the first failing field and its reason, for example:

- `Arguments do not match the tool schema at operations: Expected string, received number. Resend a complete JSON object with the required fields and types.`
- `Arguments do not match the tool schema at (arguments): Unrecognized key(s) in object: 'extra'. Resend ...`

The reason is capped at 120 characters, so long argument values never appear in the error.

## Installed version requires a reload

Installing a VSIX does not activate it. A running editor keeps its current extension version until you reload the window.

## Storage and rollback

This release adds no settings. API history for a rejected tool call now stores the exact arguments object instead of string params.

If you roll back to 4.2.87:

- A `task_state` read with a non-null revision fails with the generic schema error again.
- Context preview rows lose the token line, cost and counts.
