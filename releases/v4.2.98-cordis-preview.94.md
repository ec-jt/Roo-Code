# Roo Code 4.2.98 - Cordis preview 94

Extension version: **4.2.98**. Git tag: **v4.2.98-cordis-preview.94**. This is an experimental GitHub prerelease. It is not a stable release or a marketplace release.

This release fixes three defects found in the S2 evaluation rerun on 4.2.97. Two are in evaluation recording (experiment `evaluationRecording`, ADR-2026-11-20-feature-gating-evaluation-and-lessons). One is a missing notice when a mode selection changes the provider profile.

## Fixed: a completed task was recorded as "abandoned" (D1)

Before this release, the stop reason `completed` was written only when the extension received `yesButtonClicked` on the `completion_result` ask. The chat view's **Start New Task** button on a completed task sends `clearTask`. That aborts the task, and the abort path wrote `abandoned`. So no ordinary UI action recorded `completed` for a completed top-level task.

Now:

- `AttemptCompletionTool` sets an in-memory flag on the task's recorder (`EvaluationRecorder.completionReached`) just before it issues the `completion_result` ask.
- `abortStopReason` returns `completed` when that flag is set, or when the last ask is `resume_completed_task`. A user cancel (`user_cancelled`) still returns `user-stopped`.
- If the user sends feedback at the completion ask, the task continues and the flag is cleared. A later close is then recorded as before (`abandoned`, `error` or `user-stopped`).
- `clearTask` behaves as before. The abort path emits no `TaskCompleted` event. Only the recorded stop reason changes.
- Subtasks still record `completed` on their return path.

## Fixed: closing the window at `completion_result` wrote no stop (D2)

Cause: on window close, VS Code deactivates the extension. The sidebar `ClineProvider` is not in `context.subscriptions`, so it is never disposed, and `deactivate()` only cleaned up MCP servers and terminals. `abortTask` was therefore never called for the open task, and no stop was queued. `EvaluationRecorder.flush()` was not awaited anywhere on shutdown. Editor-tab providers are disposed when their panel closes, but the stop was queued inside `abortTask` and not awaited before the host could exit.

Now:

- New `recordShutdownStop()` in `evaluation-recording.ts` records the stop for a task and waits for the write, at most 1.5 s. It uses `completed` after a completion ask and `abandoned` otherwise (same rules as `abortStopReason`). It never throws.
- `ClineProvider.dispose()` calls it first, through the new `ClineProvider.recordShutdownEvaluationStop()`, before it removes the task.
- `deactivate()` in `src/extension.ts` calls it for every live provider before the existing cleanup.
- The recorder keeps the first stop only, so the later `abortTask` call during disposal does not overwrite it.

## New: notice when a mode selection changes the provider profile (D3)

When no task is open and the selected mode has a saved provider profile, selecting the mode switches to that profile. This is existing, intended behaviour and is unchanged. It is now visible: a VS Code information message says, for example, "Mode Architect uses profile opus. Profile changed from deepseek."

- The notice is shown only when the active profile actually changes.
- It is never shown during an open task. There the task keeps its model (Q-USE-1), and no profile change happens.
- New string `common:info.mode_profile_changed` in all 18 extension locales (C-7).

## Changes

- `src/core/task/evaluation-recording.ts`: `EvaluationRecorder.completionReached`; `abortStopReason` accepts `completionReached` and returns `completed`; new `recordShutdownStop()` and `SHUTDOWN_FLUSH_TIMEOUT_MS`.
- `src/core/task/Task.ts`: `abortTask` passes the recorder flag to `abortStopReason` (one call site, R-1).
- `src/core/tools/AttemptCompletionTool.ts`: sets the flag before the completion ask and clears it on feedback.
- `src/core/webview/ClineProvider.ts`: `recordShutdownEvaluationStop()`, called first in `dispose()`; the profile notice in `handleModeSwitch()`.
- `src/extension.ts`: `deactivate()` records and flushes a stop for each live provider.
- `src/i18n/locales/*/common.json`: `info.mode_profile_changed`.
- No change to the webview, to `clearTask` or to stored data formats.

## Validation

- `cd src && npx vitest run core/task/__tests__/evaluation-recording.spec.ts core/tools/__tests__/lesson-offer.spec.ts core/webview/__tests__/ClineProvider.lockApiConfig.spec.ts`: passed.
- `cd src && npx vitest run core/webview/__tests__/ClineProvider.sticky-mode.spec.ts core/webview/__tests__/ClineProvider.sticky-profile.spec.ts core/tools/__tests__/attemptCompletionTool.spec.ts`: passed. `ClineProvider.spec.ts` has 12 failures in edit-message and background-mode tests (for example, `Cannot read properties of undefined (reading 'revision')`). They do not exercise the changed code. They were not rerun on an unmodified tree.
- `tsc --noEmit -p .` in `src` passed. `eslint` on the changed files found no problems.

Not verified yet: a live session that closes a window at `completion_result`. The extension host may give `deactivate()` less time than the 1.5 s bound on some platforms.

## Storage and rollback

The only write is the existing single `stop` entry in the task's own `evaluation.json` (C-5). No new files and no rewrite of task data. Older versions read the file unchanged.
