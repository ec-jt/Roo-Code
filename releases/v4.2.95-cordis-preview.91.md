# Roo Code 4.2.95 - Cordis preview 91

Extension version: **4.2.95**. Git tag: **v4.2.95-cordis-preview.91**. This is an experimental GitHub prerelease. It is not a stable release or a marketplace release.

This release removes the pre-send size estimate for profiles with a context window override. Context reduction now runs only after the provider rejects a request for size, for all profiles (constraint C-6).

## Change

4.2.90 added a check that ran before each request when a profile had a context window override. It estimated the size of the pending request. If the estimate was larger than the overridden window, it compacted the context before sending.

That check is removed. All profiles now behave the same way:

1. The request is sent as is.
2. If the provider rejects the request because the context is too large, Roo runs one context reduction (a summary, or a shortening of the latest tool results when there is no earlier history to summarize).
3. Roo retries the request once.

## Effect for override profiles

The context window override still sets the context window shown in the UI and the token budget for summaries. It no longer causes compaction by itself. A model whose real window is larger than the override can therefore grow past the override without compaction, until the provider rejects a request.

## Unchanged

- The recovery after a provider context-limit rejection: one reduction, then one retry.
- The 4.2.91 path that shortens the latest tool results when there is no earlier history to summarize.
- The 4.2.92 "Context too large" warning row, the provider start time recorded by the request after recovery, and the single error row.
- The 4.2.89 check inside recovery: after a summary, oversized kept tool results are shortened, and a prompt that still exceeds the window is not sent.

## Changes

- `src/core/task/Task.ts`: removed the pre-send overflow branch in the request path, the `preSendMark` field and its assignment after dispatch, and the `estimatePendingRequestTokens()` method.
- `src/core/task/__tests__/task-model-dispatch.spec.ts`: removed the tests for the pre-send estimate and for compaction before sending. Rewrote the override tests to expect recovery only after a provider rejection. Added a test that sends a history larger than the overridden window without recovery first, and recovers only after the mocked provider rejects it.

## New experiment: Evaluation recording (off by default)

Settings > Experimental has a new experiment, **Evaluation recording** (`evaluationRecording`), defined by ADR-2026-11-20-feature-gating-evaluation-and-lessons. It is off by default. When it is off, nothing changes.

When it is on, each new task writes one file, `evaluation.json`, in its own task folder:

- **Manifest,** written when the task starts: extension version (and build commit, when the build sets one), provider, model ID, mode, profile (`cordis` or `modes`), a SHA-256 digest of the settings that affect behaviour, the same settings in plain form (experiments, architecture context mode, auto-condense, the overflow options, the text-only turn policy, the context window override, reasoning effort), and a SHA-256 hash of the first message.
- **Stop reason,** written once at the first terminal event: `completed`, `user-stopped`, `error`, `mistake-limit` or `abandoned`, with the time and the number of model requests. Later events do not change it.

Rules:

- No prompt text, API keys, base URLs or headers are written. Only hashes (16 hex characters) and plain IDs (Q-SEC-2).
- The flag is read once, when the task is created. A task created while the flag was off never gets the file. A resumed task only adds a missing stop reason to its own existing file.
- Only the task's own folder is written. Existing task data is never listed, migrated or rewritten (C-5).
- Writes are atomic and best effort. A write failure is logged and never fails or blocks the task.
- Delegating to a subtask does not record a stop for the parent.

Files: `src/core/task/evaluation-recording.ts` (new), small hooks in `src/core/task/Task.ts`, `src/core/tools/AttemptCompletionTool.ts` and `src/core/tools/NewTaskTool.ts`, the experiment ID in `packages/types/src/experiment.ts` and `src/shared/experiments.ts`, and the setting name and description in all 18 webview locales.

## Save lessons (project memory sub-toggle)

**Save lessons** is a new checkbox in Settings > Memory, under **Enable project memory**. It is off by default and is disabled while project memory is off. Turning it on needs a native confirmation. The confirmation states that lessons are stored for this project and are sent to the model provider on recall.

When it is on, the memory tool may save project topics of the new type `lesson`. The lesson body must contain the lines `cue:`, `lesson:` and `evidence:`, and may contain `confidence:` (`low`, `medium`, `high` or 0 - 1). The evidence must name the task ID and the request or tool call. A lesson that does not have these is rejected with the error code `INVALID_LESSON`. The existing secret checks apply.

- **Gate:** project memory on AND Save lessons on. The memory tool checks this before approval and after approval, and the store checks it again inside the commit. When the toggle is off, the tool returns a message that tells the model how the user can turn it on. This is not a schema failure, and nothing is saved.
- **Not gated:** reading, recalling, forgetting and clearing existing lessons. These follow the normal project memory rules.
- **NO_ENTRY:** the tool description tells the model to save a lesson only with concrete evidence from the current task. Otherwise it saves nothing, and no tool call is needed.
- **Recall:** lessons appear in the existing recall index (16 KiB budget) with the label `(lesson)`, as lower-trust data (Q-SEC-1).
- **No background work:** there is no extra model call and no summarizer.
- **Not included:** offering task-state `failedApproaches` entries as lessons at `attempt_completion` is planned for a later release.

## Storage and rollback

No change to existing storage. With Evaluation recording on, new tasks add `evaluation.json` to their own folder; older versions ignore it. After a rollback to 4.2.90 - 4.2.94, the pre-send estimate for override profiles returns, and the `evaluationRecording` setting is ignored.

Save lessons stores its toggle in a separate file, `memory/controls/<project key>.lessons-consent.yaml`. The memory consent document is not changed. Older versions ignore the new file, so project memory consent stays valid after a rollback. An older version does not know the `lesson` type. It reports each lesson topic as an invalid topic (`Invalid memory type`), does not recall it, and does not delete it. In that project, the older version blocks saving and "Forget all", and it cannot forget a lesson topic either (its read step rejects the type). To recover in an older version, delete the lesson topic file by hand, or return to this version and forget the lessons there.
